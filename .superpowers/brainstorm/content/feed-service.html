⭐ Timeline 信息流架构（评审重点）— 混合模式 Fanout：Push 为主 + Pull 兜底

PUSH · 写扩散

普通用户（粉丝 ≤ 1000）→ 发帖即推送

发帖时把 post_id 写入所有粉丝的 feed:home:{follower_id} ZSet。读时间线 O(1) 直接 ZREVRANGE，读延迟最优。写放大 = 粉丝数。

PULL · 读扩散

大 V 用户（粉丝 > 1000）→ 读时拉取

发帖不推送，只写自己的 feed:inbox:{author_id}。粉丝读时间线时拉取关注的大 V 帖子 + 自己的 push 流，内存合并排序。避免明星发帖造成海量写放大（发帖风暴）。

⚠️ 后续优化点：关注大量对象时，Pull 需多次查询 inbox，存在开销放大问题（可引入批量拉取/缓存合并）

1
发帖：PostService 本地事务写 posts 表 → 快速响应客户端，不阻塞发帖主流程 → 事务提交后生产 post:created
2
Fanout Worker（异步消费 post:created）：推送粉丝 Timeline 的 Fanout 逻辑交由异步 Worker 执行，不阻塞发帖主流程 → 查作者粉丝列表（user:followers ZSet 缓存）
3
分支：粉丝数 ≤ 1000 → Push：post_id 批量 ZADD 进每个粉丝的 feed:home:{uid}；粉丝数 > 1000 → Pull：只写自己的 feed:inbox:{author_id}
4
读时间线：TimelineService 读取 feed:home:{uid}（push 流）+ 各关注大 V 的 feed:inbox（pull 流）→ 按 score（时间戳）合并 → ZREVRANGEBYSCORE 游标分页返回
5
缓存穿透保护：ZSet 命中 → 直接返回；未命中 → 回源 MySQL 查询最近 50 条关注者帖子重建缓存（读穿 + 重建锁）
6
容量控制：每个 ZSet 限制 500 条，超出淘汰最旧；TTL 7 天滑动续期，防止大 key 无限增长
7
一致性策略：帖子删除/更新不批量清理所有用户 Timeline；前端读取列表后，对帖子状态二次校验，过滤已删除/无效动态
8
关注变更处理：新增关注 → 拉取目标作者近期帖子写入用户 Timeline；取消关注 → 清理该作者相关动态（消费 user:follow-changed）

数据库表 (feed_db)

posts
id PK · user_id IDX · content FULLTEXT · media_url · like_count · comment_count · created_at IDX
⚡ content 建 FULLTEXT 索引（MySQL 原生全文检索，ES 同步后搜索走 ES）
post_likes
post_id + user_id PK FK→posts.id · created_at
⚡ 联合主键 → 点赞天然幂等
post_comments
id PK · post_id IDX · user_id · content · created_at
outbox_events
id PK · topic · payload · status IDX · retry_count · created_at
📤 本地消息表（发件箱模式）：依托本地表保障 Kafka 投递，Worker 异步投递；配套定时补偿任务，扫描 status=pending 的事件重试发送失败消息

Redis 缓存策略

feed:home:{user_id}ZSetTTL 7d 续期
主页时间线（Push 流）· score=发布时间戳 · member=post_id · ZREVRANGEBYSCORE 分页 · 上限 500 条
feed:inbox:{author_id}ZSetTTL 7d 续期
大 V 发帖流（Pull 流）· 粉丝读时合并拉取
post:detail:{id}StringTTL 30min
帖子详情缓存 · JSON 序列化 · 更新后删除
post:likes:{id}StringTTL 30min
点赞计数缓存 · 近似值，最终数据以 MySQL 为准（异步回写校准）
feed:lock:{user_id}SETNXTTL 5s
时间线重建锁 · 防止缓存击穿并发回源

ES 同步链路（MySQL → Kafka → ES）：

发帖/点赞/评论 → 本地事务写 feed_db（MySQL 为帖子权威数据源）→ outbox_events（发件箱）→ Worker 投递 post:created / post:liked 到 Kafka
→ ES Sync Consumer 消费 → 写入 Elasticsearch（posts 索引：content + author_id + created_at）
→ 搜索接口读 ES（不读 MySQL）· ES 仅提供全文检索能力，不作为主写入存储
