⭐ 统一事件消费模型（全事件汇总）

👤 来自 User Service user:follow-changed — 有人关注了你
📰 来自 Feed Service post:created — 你关注的人发帖
📰 来自 Feed Service post:liked — 有人赞了你的帖子
🎬 来自 Video Service video:transcoded — 你的视频转码完成
📰 来自 Feed Service post:commented — 有人评论了你的帖子
1
所有业务事件统一进入 Kafka（单一事件源，业务服务只发事件不做推送）
2
Notification Service 作为 统一消费者，订阅全部相关 Topic（consumer group: notification-group）
3
事件路由规则：按事件类型 + 目标用户组装站内消息 → 写 MySQL → 更新 Redis 未读数 → 实时推送
4
消费幂等：依托 biz_unique_id（事件唯一标识）实现消息去重，先查询数据库是否已存在该消息（DB 唯一索引 + Redis SETNX 双保险），避免 Kafka 重复消费生成重复通知
5
流量管控：Kafka 消费支持限速（rate limit）+ 批量写入（攒批落库），应对大 V 发帖/热点事件产生的消息洪峰，保护下游 MySQL

⭐ WebSocket 网关转发链路

1
连接建立：前端 GET /ws/notifications → Gateway 完整走鉴权层（JWT + 黑名单）→ 升级 WS → Gateway 代理转发到 Notification Service
2
连接管理：Notification Service 维护 conn:{user_id} → ws 内存映射（+ Redis 记录在线状态，支持多端/多副本）
3
消息推送：站内消息落库后 → 查连接映射 → 有连接：WS 实时推送；无连接：仅落库 + 未读数 +1（下次上线拉取）
4
心跳保活：WS Ping/Pong 30s 间隔，断线自动重连；多实例部署时用 Redis Pub/Sub 广播到对应实例的连接

内部三层架构

Handler 层 (gRPC / WS 入口)
NotificationGrpc — GetNotifications / MarkRead / MarkAllRead / GetUnreadCount
WS Handler — 连接升级、消息收发
协议解析 + 连接管理，无业务逻辑
Service 层 (业务核心)
KafkaConsumer — 统一事件消费 + 去重
MessageService — 站内消息组装 / 已读处理
PushService — WS 实时推送 / Redis Pub-Sub 广播
➤ 消费 user:follow-changed / post:created / post:liked / post:commented / video:transcoded
Repository 层 (数据访问)
Prisma / Sequelize — MySQL 操作
ioredis — 未读数、连接状态、去重
事务边界：消息落库 + 未读数更新

外部依赖

gRPC ⟷ Gateway — 查询/已读接口
WS ⟷ Gateway — WebSocket 代理转发链路
Kafka ⟵ user:follow-changed / post:liked 等全量事件
MySQL ⟷ notify_db（独立库）
Redis ⟷ 未读数 / 在线状态 / 消费去重 / Pub-Sub

数据库表 (notify_db)

notifications
id PK · user_id IDX · type · actor_id · ref_id · content · is_read IDX · biz_unique_id UNIQUE · created_at IDX
type: follow / like / comment / post / video_ready · ref_id 指向业务对象 · biz_unique_id 唯一索引支撑消费幂等
🔄 生命周期：可配置消息保存周期（默认 30 天），定时归档清理历史消息，控制数据库容量
kafka_offsets
topic + partition PK · offset · updated_at
📌 手动提交 offset 记录 · 配合 Redis 去重实现 exactly-once 效果

Redis 缓存策略

notify:unread:{user_id}StringTTL 7d 续期
未读数 · 新消息 +1 · 已读清零/减量 · 首页角标读取 O(1) · 支持 MySQL 兜底重建（缓存失效时按 is_read=0 计数回填，防数据不一致）
notify:dedup:{event_id}SETNXTTL 24h
消费幂等去重 · Kafka 重复投递只处理一次
ws:online:{user_id}StringTTL 心跳间隔×3
在线状态 · 多端连接计数 · 心跳续期
notify:recent:{user_id}ListTTL 1h
最近 N 条消息缓存（下拉刷新免查库）· 上限 50 条 LPUSH + LTRIM

推送模型总结：

在线（WS 已连接）→ 落库 + Redis 未读数 +1 + WS 实时推送
离线断线保障 → 离线期间消息持久入库，重连后客户端主动拉取全部离线通知，不丢消息
多端（Web/移动端同时在线）→ Redis Pub/Sub 广播到连接所在实例，各端同时收到
多端已读同步 → 任意设备标记已读，同步更新数据库 is_read + 扣减 Redis 未读数，所有登录终端状态统一
已读回执 → MarkRead 更新 MySQL is_read + 扣减 Redis 未读数
