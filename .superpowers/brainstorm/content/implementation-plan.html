📐 实现计划（A/B 计划对比）

横向全量 vs 纵向切片 · 两条路线 · 一次选择

计划 A：横向全量 一步到位

一次性搭建全部 6 个微服务 + 全部中间件 + 前端 3 个 Remote，最后统一联调。
P1基础设施：Kind 集群 + MySQL/Redis/Kafka/ES/MinIO + Ingress 全部就位
P2后端并行：6 个服务同时开写（gRPC + 表结构 + 核心逻辑）
P3前端并行：Shell + 3 Remote + 全部页面
P4联调收尾：统一联调 → 修 bug → 演示

计划 B：纵向切片 最小闭环先行

先打通一条最小完整链路（发帖 → 时间线），跑通后再逐模块横向扩展。
P1最小闭环：Shell + Feed Remote + Gateway + Feed Service + MySQL/Redis → 「发帖 → 首页时间线」端到端跑通
P2用户域：User Service + 注册/登录/关注 + JWT 鉴权接入
P3视频域：Video Service + S3 分片 + FFmpeg 转码 + HLS 播放
P4增强域：Kafka 事件化 + Notification + ES Search + 通知抽屉

⭐ 对比

计划 A：横向全量计划 B：纵向切片
首个可见成果慢（全部完成后才有）快（P1 即可演示发帖/时间线）
风险集成风暴 — 问题集中在最后爆发，难定位增量集成 — 每步小风险，即时消化
改动成本低（一次设计一次写）中（P2 后需回填 Kafka 事件化改造 Feed）
学习价值高（全面覆盖所有技术点）高（每步都有完整可运行成果）
中途可控性低（中途无法演示/验收）高（每个阶段都能演示、可随时停下）
总工期理论最短（并行最大化）略长（有回填成本）

✅ 推荐：计划 B（纵向切片）

理由：本项目的目标是学习/演示 — 纵向切片让每个阶段都有可运行、可演示的成果，学习曲线平缓；集成风险分散，出问题好定位。
关键点：P2 回填 Kafka 事件化时，Feed 的发帖逻辑需改为 outbox 模式 — 设计已预留（outbox_events 表 + Worker），回填成本可控。
里程碑：P1「发帖 → 时间线」→ P2「账号/关注」→ P3「视频」→ P4「通知 + 搜索」— 每阶段结束都有一次完整演示。
