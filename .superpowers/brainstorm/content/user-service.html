内部三层架构

Controller 层 (gRPC 入口)
UserServiceGrpc — Register / Login / GetProfile / UpdateProfile / Follow / Unfollow / GetFollowers / GetFollowing
仅做参数校验 + 协议转换，无业务逻辑
Service 层 (业务核心)
AuthService — 密码 BCrypt 加密、JWT 签发
UserService — 资料 CRUD
FollowService — 关注关系（写 MySQL + 发 Kafka）
➤ 生产 user:registered
➤ 生产 user:follow-changed
Repository 层 (数据访问)
MyBatis-Plus / JPA — 数据库操作
Redis 缓存读写 — 关注列表、用户资料缓存
事务边界：关注操作在本地事务内完成 MySQL 写入

外部依赖

gRPC ⟷ Gateway — 接收 HTTP→gRPC 转发的用户请求
Kafka ➤ user:registered（注册成功）
Kafka ➤ user:follow-changed（关注变更）
MySQL ⟷ user_db（独立库）
Redis ⟷ 缓存（Session / 关注列表 / 资料）

缓存一致性策略：更新数据库 → 删除 Redis 缓存，TTL 作为并发场景兜底方案

数据库表 (user_db)

users
id PK · username UNIQUE · email UNIQUE · password_hash · bio · avatar_url · created_at · updated_at
follows
follower_id + followee_id PK FK→users.id · created_at
⚡ (user_id, followee_id) 联合唯一索引 → 关注操作天然幂等
user_sessions
token_id PK · user_id FK→users.id · expires_at IDX · revoked
📱 管控多端登录、主动下线 · Redis Token 黑名单作为短期兜底方案，与网关共享
⚠️ 演示环境使用数据库物理外键；正式生产环境移除物理外键，由业务代码维护关联完整性

Redis 缓存策略

user:profile:{id}StringTTL 10min
用户资料热点缓存 · 更新数据库后删除缓存 · TTL 兜底并发场景
user:followers:{id}ZSetTTL 5min
粉丝列表 · ZRange 分页读取，规避大 key 风险
user:following:{id}ZSetTTL 5min
关注列表 · ZRange 分页读取，规避大 key 风险
auth:blacklist:{jti}StringTTL = JWT 剩余有效期
登出 Token 黑名单 · 与 Gateway 共享

关注流程（事务 + 事件）：

① FollowService 在本地事务内写 follows 表 + 更新粉丝/关注数
② 事务提交成功后生产 user:follow-changed 到 Kafka
③ 采用 事务监听机制（@TransactionalEventListener AFTER_COMMIT），事务提交后才发事件，降低消息丢失风险
④ Feed Service 消费该事件，更新关注者的时间线候选
⑤ 若事件生产失败，通过本地消息表兜底补偿重发
