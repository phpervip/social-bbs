⭐ MySQL → Kafka → ES 异步同步链路

1
写入源：Feed Service 发帖/删帖/更新时，事务内写 MySQL + outbox_events（发件箱）→ Worker 投递 post:created / post:deleted / post:updated 到 Kafka
2
ES Sync Consumer：Search Service 消费同步事件（独立 consumer group: es-sync-group），解析 payload → 组装 ES 文档
3
写入 ES：index()（新增/更新）或 delete()（删除）→ 文档写入 posts 索引
4
一致性保障：消费 Kafka 事件依靠业务唯一标识（biz_unique_id）实现幂等，防止重复消费造成 ES 文档错乱 · ES 写入失败 → 重试（有限次）+ 失败落 dead-letter 表，定时补偿任务重放 · 最终一致（秒级延迟）
5
增量同步兜底：定时（每 10min）扫描 MySQL 增量（updated_at > last_sync），对比 ES 数据修复遗漏，保证长期一致性
⚠️ 一致性边界：本方案属于最终一致性架构，MySQL → ES 存在短暂同步延迟（秒级）。强实时场景（如帖子详情、编辑后立即读取）直接读取 MySQL，ES 仅服务搜索场景，不做强一致承诺。

⭐ 帖子全文检索 · 筛选 · 排序

// posts 索引 Mapping（简化）
content text (ik_max_word 中文分词 + standard 英文)
author_id keyword · created_at date · like_count long · has_video boolean · media_type keyword
⚠️ 依赖备注：ES 需部署 IK 分词器插件（ik_max_word / ik_smart），保障中文全文检索效果；未部署则中文只能按单字/整词匹配
1
检索：multi_match 对 content 全文检索（BM25 相关性评分）· 查询词高亮返回（highlight）
2
筛选：组合 filter 精确过滤 — 按作者（author_id）、时间范围（created_at range）、类型（media_type）、是否含视频（has_video）
3
排序：双模式 — _score（相关度，默认）· created_at desc（最新）· like_count desc（热门）；function_score 时间衰减混合排序（新帖加权）
4
分页：当前采用 from/size 分页，前端限制最大页码（如 100 页），避免深页性能劣化 · 海量翻页场景可迭代升级为 search_after 游标分页（预留演进空间）
5
用户搜索：同样走 ES users 索引（username 前缀匹配），返回用户 + 帖子混合结果

内部三层架构

Handler 层 (gRPC 入口)
SearchGrpc — SearchPosts / SearchUsers / GetSearchSuggest
参数校验 + 协议转换，无业务逻辑
Service 层 (业务核心)
SearchService — 检索 DSL 组装 / 结果处理
SyncService — ES 同步消费 + 幂等 + 重试
CompensationService — 增量扫描 / dead-letter 补偿
➤ 消费 post:created / post:deleted / post:updated
Repository 层 (数据访问)
go-elasticsearch — ES 读写
GORM / sqlx — MySQL 增量扫描
go-redis — 检索缓存
ES 是唯一检索数据源，MySQL 仅用于补偿扫描

外部依赖

gRPC ⟷ Gateway — 搜索接口
Kafka ⟵ post:created / post:deleted / post:updated（同步事件）
MySQL ⟷ feed_db（只读，增量补偿扫描）
Redis ⟷ 检索结果缓存 / 热门词缓存
ES ⟷ posts + users 索引（主检索源）

ES 数据一致性 & 增量同步

最终一致（秒级延迟）：业务写 MySQL 是唯一权威，ES 异步同步
幂等消费：biz_unique_id 去重，重复投递不重复写
失败重试：ES 写入失败自动重试 3 次 → 仍失败进 dead_letter 表，定时任务补偿重放
死信运维：死信表数据支持后台人工重试（Web 管理界面一键重放），已处理记录定期清理（保留 7 天），避免死信表无限膨胀
增量兜底：每 10min 扫 MySQL 增量（updated_at 游标），修复漏同步数据
降级开关：ES 故障时检索自动降级为 MySQL FULLTEXT（posts.content LIKE）或直接返回热门缓存，保证搜索可用性

Redis 缓存策略

search:result:{query}:{page}StringTTL 5min
检索结果缓存（JSON 序列化）· 高频词命中缓存免查 ES · 依靠 TTL 自动过期，帖子更新后存在短暂缓存不一致（可接受，搜索非强实时）
search:hot:{day}ZSetTTL 24h
热搜词榜 · 搜索次数计数 · 搜索框联想数据源
search:suggest:{prefix}StringTTL 10min
搜索联想缓存 · 前缀命中直接返回 · 减少 ES suggest 调用
es:circuit:openStringTTL 30s
ES 熔断标记 · 连续失败置位 · 触发期间走降级路径

降级策略（三级）：

L1 正常：Redis 检索缓存命中 → 免 ES 查询
L2 ES 可用：走 ES 全文检索（BM25 + 筛选 + 排序）
L3 ES 故障：熔断标记开启 → 降级 MySQL FULLTEXT 检索 或 返回热门帖子缓存列表 + 提示「搜索结果可能不完整」
恢复：熔断 30s 后半开探测，ES 恢复自动回到 L2
